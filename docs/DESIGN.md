# 设计说明

## 目标与非目标

Cellcloak 面向**已经聚合的二维计数表**，把发布前审查做成可重复的本地流水线：契约固定规则，算法固定选择顺序，输出分为可公开发布物与内部证据。它刻意不接入分布式求解器、不尝试差分隐私、也不处理个人明细。

## 模块与数据流

```text
YAML contract
   │  contract.load_contract：安全解析、路径约束、静态校验
   ▼
TableSpec ── ingest.load_table ──► TableModel（完整矩阵、边际、输入哈希）
                                      │
                                      ▼
                           risk.classify（主风险标签、主抑制坐标）
                                      │
                                      ▼
                     suppress.suppress_table（主抑制 + 互补抑制）
                                      │
                                      ▼
                     verify.verify_table（独立边际与反推核验）
                                      │
                    ┌─────────────────┴──────────────────┐
                    ▼                                    ▼
       report.emit_outputs                        ledger.Ledger
       public/ 与 audit/                          SQLite 台账
                    │                                    │
                    └──────────── pipeline ──────────────┘
                                 │
                      CLI / loopback Flask UI
```

各阶段只通过不可变或显式数据对象传递结果。核验器不读取抑制器的内部评分或中间状态，而是从矩阵、抑制映射和边际重新计算。

## 模型与稳定性

- `TableModel` 保存声明顺序、完整计数映射、源文件名与 SHA-256。矩阵必须覆盖 `row_order × col_order`；边际总是重新计算。
- 单元格指纹为 `SHA-256("cellcloak-cell-v1", table_id, row, col)`。它**不包含计数**，因此报告和页面可以稳定标识坐标，同时不因指纹暴露小计数值。
- 运行 ID 格式为 `run-<UTC 微秒时间戳>-<随机后缀>`，按字符串可排序；相同输入重复运行会生成新记录，不覆盖旧运行。
- 时间戳使用 UTC ISO 8601；文件统一 UTF-8。

## 主风险分类

对每个单元格：

1. 在 `always_suppress` 中 → `forced`。
2. 计数为 0 且在 `structural` 模式下被声明为结构零 → `safe`。
3. 计数为 0 → `sampling_zero`。
4. `0 < count < min_count` → `small_count`。
5. 其他 → `safe`。

分类前检查声明结构零是否确实为 0。报告与台账使用同一风险标签，但报告只展示标签、计数统计和坐标，不展示被抑制原始值。

## 互补抑制

### 停止条件

一条行/列如果包含恰好一个被抑制单元格，就可以由该行/列的公开合计减去其他可见值直接得到该单元格，因此必须再抑制一个可见单元格。算法反复扫描所有行和列，直到没有任何这样的单元素行/列，或触发阻断。

### 扫描与即时更新

扫描顺序固定为 `row_order` 全部行，然后 `col_order` 全部列。每选择一个补抑制单元格就立即写入抑制映射，因此在同一轮中，一个补抑制单元格可以同时关闭相邻行/列的单未知数状态。这样比“整轮快照后再统一应用”更少产生无谓级联。

### 候选评分

升序排序键：

```text
(count, loss_weight, row_key, col_key)
```

`loss_weight` 来自契约，未声明为 `1.0`。计数较小优先降低被隐藏计数总量；权重是显式的信息损失偏好；最后用行键、列键保证跨平台、跨运行确定性。候选只会来自当前可见单元格。

### 阻断

任一情况出现即判该表 `blocked`：

- 初始主抑制比例已经超过 `max_suppression_ratio`；
- 某单元素行/列没有可见候选；
- 完成一轮后抑制比例超过上限；
- 扫描轮次耗尽 `max_suppression_rounds`。

只要一次运行中任一表 `blocked`，整次运行状态为 `blocked`，不生成任何公开 CSV。审计仍会记录已有抑制映射与原因，便于复核，但不会把局部结果当成可发布表。

### 信息损失摘要

- 被抑制单元格数量与比例；
- 被抑制计数总和占全表计数总和比例；
- 最大单行抑制比例；
- 最大单列抑制比例。

这些是聚合统计，不包含单格原始值。

## 独立核验

`verify_table` 只读取矩阵、抑制映射、主抑制坐标和比例上限：

1. **边际一致性**：重算每行、每列与总计，并校验三组汇总相等。
2. **抑制映射有效性**：坐标必须存在，类型必须是 `primary` 或 `secondary`。
3. **主抑制覆盖**：契约风险识别出的每个主抑制坐标必须仍被抑制。
4. **比例上限**：重新计算抑制比例。
5. **单未知数行/列**：独立统计恰好一个抑制单元格的行和列。
6. **重建攻击模拟**：仅根据公开边际关系，反复寻找“某行/列只剩一个未知数”的路径并级联消元；任何被恢复的抑制单元格都失败。
7. **逐单元格证据**：坐标、指纹、抑制类型、风险类别、行/列抑制数、是否可直接推导。

运行状态判定顺序：存在阻断表 → `blocked`；否则核验失败 → `verify_failed`；否则 `ok`。核验失败不生成公开表。

`verify --run` 从 SQLite 重建矩阵与抑制映射，再运行同一独立核验，并把结果追加为 `source = reverify` 的 checks。原运行已被阻断时保留 `blocked` 状态。

## 报告与发布

- `public/<table_id>.csv` 仅对 `ok` 运行生成。被抑制单元格写为 `NA`，保留行/列/总合计，供下游发布分析使用。由于所有单元素行/列已消除，这些合计不能直接反推任一抑制值。
- `audit/report.json` 是机器可读的完整证据；`report.md` 与自包含 `report.html` 供人工审阅。HTML 的所有样式内联，不引用外部脚本、字体、样式或图片。
- 报告不包含抑制单元格原始计数；原始计数只进入本地 SQLite `cells` 表。报告中的输入哈希、风险类别、计数统计与指纹用于复核。
- 输出目录带 `.cellcloak-output.json` 清单。工具只清理清单中记录的自有文件；遇到无清单但已有 `public/` 或 `audit/` 内容的目录会拒绝覆盖。

## SQLite 台账

| 表 | 用途 |
| --- | --- |
| `runs` | 运行 ID、数据集、状态、开始/结束、契约哈希、输出目录、汇总 JSON |
| `tables` | 表维度、主/补抑制数、比例、状态、阻断原因、元数据 |
| `cells` | 每个单元格的原始计数、抑制类型、风险类别、指纹；**仅内部** |
| `checks` | 每项核验结果与证据摘要 |
| `artifacts` | 产物路径、类型、SHA-256 |
| `purge_tombstones` | 清除墓碑：`run_id`、状态（`purging`/`purged`）、原因码、时间戳、聚合结果 |

台账连接在每次操作中创建并提交，启用外键；所有写操作使用 SQLite 事务。`runs` 不覆盖历史记录。`diff` 比较抑制比例、主/补抑制、阻断状态、表状态与公开 CSV 哈希。`purge_tombstones` 不挂外键：清除会级联删除 `runs` 行，墓碑必须独立存活。表结构通过 `CREATE TABLE IF NOT EXISTS` 随连接自动迁移，旧数据库打开即升级。

## 保留期清除（forget）

`forget --run <id> --reason <code>` 删除指定 run 的原始单元格记录与内部报告文件。数据库事务与文件删除无法共同原子提交，因此采用**路线 A** 的可恢复生命周期：

```text
事务 1：写入 purging 墓碑（含候选文件清单 manifest）
   ↓ 崩溃 → 重跑 forget 从墓碑 manifest 续做
逐项：重新核验候选文件并删除（幂等）
   ↓ 崩溃 → 已删文件在续做时得到 already_absent
事务 2：级联删除 runs/tables/cells/checks/artifacts 行，
        同事务把墓碑标为 purged、写入聚合结果、清空 manifest
```

事务 2 把路线 A 描述中的“级联清空”和“标记 purged”合并为一个原子提交，消除了两者之间的崩溃窗口；若该事务崩溃则整体回滚，续做时两个步骤一起重做。

### 为什么选路线 A

- **重试幂等**：墓碑先行使意图先于任何变更持久化；之后每一步都幂等——文件删除按 SHA 核对、对缺失文件容忍，`DELETE ... WHERE run_id` 天然幂等，最终 UPDATE 幂等。任意崩溃点都有明确的重入语义，且续做不依赖可能已被级联删除的 `artifacts` 行（候选清单存在墓碑 manifest 里）。
- **共享目录**：文件删除从不只信台账路径。每个候选在删除当下重新对照活动状态：磁盘 SHA、其他保留 run 的引用查询、输出清单确认。共享 `--out` 目录或外部改动只会把结果变成 `kept_*`，不会误删。台账行的删除不依赖文件结果，文件被保留不会回滚原始计数的清除。
- **后来 run 覆盖旧路径**：`emit_outputs` 会在同一 `--out` 目录重写同名文件并登记新哈希，旧 run 的哈希随之失配 → `kept_hash_mismatch`；若后来的 run 仍保留，其 `artifacts` 行还会触发 `kept_shared_reference`。路线 B（先备份/暂存文件、再一个事务清库、最后清理暂存）在“文件已暂存、事务未提交”的窗口崩溃时，需要在暂存目录与数据库两个持久状态之间做恢复取舍，且暂存目录本身同样面临共享与覆盖问题；路线 A 让台账墓碑成为唯一事实来源，文件系统只是可反复重验的状态，更契合“无法共同原子提交”的现实。

### 文件安全核验

候选文件仅为台账中该 run 登记的内部报告（`audit_json`/`audit_md`/`audit_html`）。删除前依次检查：

1. 最终路径不是符号链接（`kept_symlink`）；
2. 解析后的路径仍在该 run 的输出目录内（`kept_path_escape`，拒绝 `..` 与符号链接穿越）；
3. 文件存在且为普通文件（否则 `already_absent` / `kept_not_a_file`）；
4. 输出目录的 `.cellcloak-output.json` 可解析且为本工具格式（`version: 1`），否则 `kept_marker_invalid`；
5. 相对路径在清单 `artifacts` 中，否则 `kept_not_in_manifest`；
6. 未被其他保留 run 的 `artifacts` 行引用，否则 `kept_shared_reference`；
7. 当前磁盘 SHA-256 等于该 run 登记的哈希，否则 `kept_hash_mismatch`。

全部通过才 `unlink`。任何保留都写入当次结果与墓碑聚合（按类别计数、按 artifact kind 记录结果），墓碑不持久化任何文件路径。

### 墓碑与可见性

- 清除后 `purge_tombstones` 只保留：`run_id`、`state = purged`、原因码、开始/完成时间、聚合结果（各类别文件计数、按 kind 的结果、各表删除行数）。不含原始计数、坐标键、内部报告路径；`purging` 期间的工作清单（manifest）在标为 `purged` 的同事务内置空。
- `runs` 列表把墓碑合并进结果：`purged` run 以墓碑行出现，`purging` run 覆盖显示状态。`get_run_detail` 对已清除 run 返回空表/空核验加墓碑。`verify` 对 `purging`/`purged` run 明确返回对应状态（退出码 4），不会用不完整状态继续核验，也不会表现得像 run 从未存在。`diff` 拒绝比较已清除 run（`E_RUN_PURGED`/`E_RUN_PURGING`）。Web 详情页对墓碑 run 返回 410。
- 重复执行 `forget` 是幂等空操作（`already_purged`）。`--dry-run` 只读：不碰数据库与文件，输出与真实执行相同的逐项判定。

## Web

Flask 应用只由 CLI 在回环地址启动。页面数据均来自本地台账；不展示 `cells` 原始计数。演示按钮调用同一个 `execute_run`，契约固定为仓库内置 `fixtures/demo/contract.yml`，没有上传或远程抓取入口。响应带 CSP、`X-Frame-Options: DENY`、`nosniff` 等本地安全头。

## 确定性、边界与限制

- 不依赖随机抑制；随机性只用于运行 ID 后缀和 Flask 会话密钥。
- 不保证抑制集合基数最小，也不保证联合边际、复杂整数约束或 3 维表的安全性。
- 单未知数核验不等于完整统计披露控制；发布者仍需结合抽样设计、表间关联、上下文信息和组织政策审查。
- 数据规模按内存中的二维表设计。若表非常宽或非常大，应在外部先做工程评估。
- 当前版本不支持同一契约内多张表之间的交叉推导。
